# Simulation Engine

The `engine` crate contains the entire turn state machine, the event log, and the `Strategy` trait. It has no I/O — it takes a `RuleSet` and a list of strategies in, and produces a sequence of events out. Everything else in the workspace is a shell around this crate (see [architecture.md](./architecture.md)).

## Turn state machine

One call, `Game::step_turn()`, advances the game by exactly one player's turn (which may itself include multiple dice rolls on doubles) and returns the events it produced. The CLI/server drive this in a tight loop until the game ends; the browser (via `engine-wasm`) drives it one call at a time, rendering between calls, which is what makes adjustable-speed playback possible without any special "slow mode" inside the engine itself — speed is purely a UI-side delay between calls.

```
step_turn():
  if player is in jail:
    resolve_jail_decision()          # may end the turn here
  loop:
    roll = roll_dice()
    record(RollDice)
    move_player(roll)                # handles passing/landing on GO
    resolve_landing()                 # purchase / rent / tax / card / jail / free parking
    if not roll.is_doubles or player now in jail:
      break
    if doubles_count == 3:
      send_to_jail()
      break
  check_bankruptcy_and_game_end()
```

## Determinism

The engine takes a single `u64` seed at game creation and derives one `rand`-compatible PRNG from it (a fast, non-cryptographic generator — reproducibility matters here, not unpredictability). Every random decision in a game — dice rolls, card shuffling and draws, auction tie-breaks — consumes from this one stream in a fixed order determined by the turn state machine. This gives the core guarantee the rest of the system leans on (see [architecture.md](./architecture.md#determinism-as-a-storage-optimization)): `(RuleSet, seed)` fully determines a game, so any game can be regenerated byte-for-byte later instead of stored.

## Event log

Every state change during a game is recorded as a typed event, in order. This is the single format used for three different purposes: driving board animation in the browser, computing every statistic in [analysis-and-metrics.md](./analysis-and-metrics.md), and (for saved single runs) the archived record itself.

Core event types (see [data-model.md](./data-model.md#event-log-entry) for the exact serialized shape):

| Event | Fired when |
|---|---|
| `RollDice` | A player rolls the dice |
| `Move` | A player's position changes |
| `PassGo` | A player passes or lands on GO and collects salary |
| `PropertyOffered` | A player lands on an unowned property |
| `PurchaseDecision` | A strategy accepts or declines a purchase offer |
| `AuctionBid` / `AuctionWon` | Each player's sealed bid, then the settled sale — see [game-rules.md](./game-rules.md#auctions) |
| `RentPaid` | Rent changes hands |
| `TaxPaid` | Income or luxury tax paid |
| `CardDrawn` | A Chance/Community Chest card is drawn, with its effect |
| `JailEntered` / `JailDecision` / `JailExited` / `UsedGetOutOfJailFreeCard` | Jail flow |
| `HouseBuilt` / `HouseSold` | Building changes |
| `Mortgaged` | A property is mortgaged (one-way in Phase 2 — see [game-rules.md](./game-rules.md#mortgaging)) |
| `Bankrupted` | A player goes bankrupt, and to whom (a player, or the bank if `None`) |
| `TradeExecuted` / `TradeDeclined` | A proposed trade (`RuleSet.trading_enabled`, Phase 7) the counterparty accepted or declined — see [game-rules.md](./game-rules.md#trading) |
| `GameEnded` | One player remains; includes the winner and final standings |

## The `Strategy` trait

A `Strategy` is asked to make every decision a human player would normally make. Built-in strategies (Buy All/Good/Bad/None — see [player-strategies.md](./player-strategies.md)) and any custom strategy implement the same trait, so the engine, the batch runner, and the UI's strategy picker all treat them identically.

```rust
pub trait Strategy {
    fn decide_purchase(&mut self, view: &GameView, player: usize, offer: &PurchaseOffer) -> bool;
    fn decide_jail_action(&mut self, view: &GameView, player: usize) -> JailAction; // PayFine | RollForDoubles
    fn decide_build(&mut self, view: &GameView, player: usize) -> Vec<BuildAction>; // build/sell house(s), once per turn
    fn decide_mortgage(&mut self, view: &GameView, player: usize, shortfall: u32) -> Vec<MortgageAction>; // mortgage and/or sell houses
    fn decide_auction_bid(&mut self, view: &GameView, player: usize, space: usize) -> Option<u32>; // None/0 = abstain
    fn decide_trade(&mut self, view: &GameView, player: usize) -> Option<TradeOffer>; // at most one proposal per turn, only when RuleSet.trading_enabled
    fn decide_trade_response(&mut self, view: &GameView, player: usize, offer: &TradeOffer) -> bool; // asks the counterparty whether to accept
}
```

`player` is passed explicitly to every hook rather than read off `view.state.current_player` — `decide_auction_bid` asks every player, not just the current one, so that shortcut doesn't hold in general. There's no `UseCard` variant on `JailAction`: a held "Get Out of Jail Free" card is always played automatically by the engine before `decide_jail_action` is even called (see [game-rules.md](./game-rules.md#jail)), since using it is never worse than the alternatives. Auction bidding is a single sealed round, not live/iterative — `decide_auction_bid` doesn't see anyone else's bid (see [game-rules.md](./game-rules.md#auctions)). `decide_trade_response` exists for the same reason `decide_auction_bid` asks every player: a trade means nothing without the other side's consent — see [game-rules.md](./game-rules.md#trading) for why this ended up as two hooks rather than the single one originally sketched here.

`GameView` is a read-only projection of the current `GameState` (see [data-model.md](./data-model.md#gamestate)) — a strategy can see the whole board, every player's holdings and cash, and its own history, but cannot mutate anything directly; all changes flow back through the engine, which is what keeps the event log complete and authoritative.

## Cards

The Chance and Community Chest decks are the classic 16-card US-edition set, built once per game and shuffled with the game's own seeded RNG (so, like everything else, deck order is a pure function of the seed). Cards that are mechanically identical — many are just "collect/pay a flat amount from/to the bank" with different flavor text (e.g. "bank error in your favor" and "you inherit $100" are indistinguishable to the simulation) — share one effect type rather than getting a named variant each; the event log records the effect and amount, not the flavor text. A drawn "Get Out of Jail Free" card is held by the player (removed from the deck) until it's used or its holder is bankrupted, at which point it returns to the bottom of its own deck (if bankrupt to the bank) or transfers to the new owner (if bankrupt to a player) — see [game-rules.md](./game-rules.md#bankruptcy).

## Interactive sessions: the human `Strategy`

Phase 9 adds server-authoritative human-vs-CPU play (`crates/server/src/interactive/`, [api.md](./api.md#interactive-sessions-phase-9)) without touching any of the turn state machine above: a human seat is just another `Strategy` implementation, `HumanStrategy`. Each of its 7 methods builds a `PendingDecision` describing what it's being asked, publishes it into state shared with the HTTP layer, and blocks the current thread (`mpsc::Receiver::recv()`) until `POST /sessions/{id}/decisions` answers it.

This only works because each session's `Game` runs on its own dedicated OS thread rather than as an async task or inside the request/response cycle: blocking a plain thread is free (unlike blocking an async executor thread), and the real Rust call stack through `Game::step_turn()`'s nested calls *is* the resume point for free — there's no hand-maintained "which decision are we waiting on" state machine anywhere, and every existing driver of the engine (CLI, batch, tournament, the archive server's `POST /runs*`, `engine-wasm`) is completely unaffected. The engine-side changes this needed, all additive:
- `strategies: Vec<Box<dyn Strategy + Send>>` (widened from `Vec<Box<dyn Strategy>>`) and `Game::with_strategies` (the same construction as `Game::new`, minus the strategy-id resolution loop `Game::new` still does), so a `HumanStrategy` can be injected at one seat.
- `Serialize`/`Deserialize` on `PurchaseOffer`/`BuildAction`/`MortgageAction`/`TradeOffer`/`JailAction`, so the server can embed these directly in its decision/answer JSON.
- `GameState::new` made `pub` (was `pub(crate)`), so the server can publish an initial snapshot before its session thread has finished constructing `Game`.
- `GameView::log_since_turn_start`, `Game::turn_cap`/`winner`/`finish`, and bounds-checked `try_build`/`try_sell_house`/`try_mortgage`/`trade_is_valid` — see the next two paragraphs for why.

A `Strategy` implementation is no longer only ever a trusted built-in: `HumanStrategy`'s answers come straight from client JSON, so a client can name any board-space index it likes in a `Build`/`Mortgage`/`TradeProposal` answer. `try_build`/`try_sell_house`/`try_mortgage`/`trade_is_valid` are bounds-checked against `BOARD_SIZE` accordingly (an out-of-range index is treated the same as every other invalid action here — a silent no-op, not a panic); the interactive server also rejects one with a 400 before it ever reaches a session's channel, for a clearer error than a silently-ignored action.

A decision published mid-turn needs the events that already happened this same turn (the roll, the move, a card draw) visible alongside it, not just at turn end — otherwise a client would see a `PendingDecision` with no idea what led to it. `GameView::log_since_turn_start` exposes exactly that (every event recorded so far in the turn currently being resolved), which is what lets `HumanStrategy::ask` flush events to a polling client the moment it publishes a decision rather than only once `step_turn` returns; the session's own end-of-turn publish and this mid-turn one dedupe against the same `seq` watermark, so nothing is ever published twice.

If a session's game thread panics, the blocked `recv()` never returns (the thread is gone), so a `catch_unwind` one level up marks the session `errored` instead. If the session is torn down mid-game instead (`DELETE /sessions/{id}`, which drops the channel's `Sender`), the blocked `recv()` returns `Err`, and each `HumanStrategy` hook falls back to the same safe/no-op default every other strategy already uses for an abstained action (decline a purchase, keep rolling for doubles rather than pay, propose/build/mortgage nothing, abstain from an auction, decline a trade) — see `crates/server/src/interactive/human_strategy.rs`.

## Batch execution

The batch runner (`engine::batch::run_batch`) takes a `RuleSet`, a list of strategy configs, and a list of seeds, and runs one full game per seed. Games are independent (no shared mutable state), so batches are parallelized trivially across seeds using `rayon`'s parallel iterators — this is the primary lever for the "tens of thousands of games in seconds" target in [Phase 3](./roadmap.md#phase-3--batch-simulation--statistics-engine). Each game produces its own event stream internally for statistics aggregation, but (per the storage decision in [architecture.md](./architecture.md#determinism-as-a-storage-optimization)) only aggregate stats and the `(config, seed)` pair are kept once the batch's summary is computed — the full per-game event logs are not retained in memory beyond that game's own aggregation step.
